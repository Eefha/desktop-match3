# 开发思路

> 这不是功能清单，是"为什么这么做"的推演过程。
> 想看怎么用，读 `README.md`；想看联机细节，读 `联机方案.md`。

---

## 一、从一句约束开始，而不是从一个玩法开始

大多数项目是从"我要做一个消消乐"开始的，那会一路走向：开始界面、关卡、皮肤、音效。
这个项目反过来，起点是一句限制：

> **屏幕上不能出现任何"游戏"的东西。**

于是所有设计都是被这条约束推出来的，不是选出来的：

| 约束 | 直接后果 |
|---|---|
| 不能有游戏感 | 没有标题栏、开始界面、按钮、说明文字、音效、震屏 |
| 画面必须像桌面 | 背景不能重画壁纸，要裁真实壁纸；图标要用系统原图；格子要套系统真实间距 |
| 随时能走 | `ESC` 立刻消失，桌面原样；退出时分数照样入榜，不必打完 |

**这条思路的价值在于：约束会替你排除 90% 的选项。** 每次纠结"要不要加个动效/音效/排行榜弹窗"，拿约束一比就有答案了，不需要争论审美。

## 二、核心取舍：每个决策都留着备选和理由

思路是否清楚，看的是"当时还考虑过什么、为什么没选"。下面这几条是整个项目的骨架。

### 2.1 动真实桌面 vs 盖一层假桌面

| | 侵入式 | 覆盖式（采用） |
|---|---|---|
| 做法 | `LVM_SETITEMPOSITION` 真挪桌面图标、`WM_COMMAND 0x7402` 隐藏真图标 | 开一个不透明窗口盖住，用提取出的图标原图重画 |
| 视觉 | 最真 | 很真（壁纸是同一张裁出来的，接缝看不出来） |
| 风险 | **程序崩了用户桌面就毁了** | 崩了也只是关掉一个窗口 |

结论：一个摸鱼工具不该承担"把别人桌面搞乱"的风险。**能用低风险方式做到 95% 的效果，就不去搏那 5%。**

### 2.2 复刻整个桌面 vs 只占左边一条

最早是整屏覆盖，连任务栏都要复刻（亚克力、固定图标、托盘、时钟都写过）。
后来发现：**真东西就在旁边，为什么要复刻？**

改成只占屏宽 58% 的一条，高度正好到工作区底边。右边 42% 和底下那条任务栏全是系统原文——真图标、真右键、真拖拽、真时钟。
复刻代码（`taskbar.py` / `deco.py` / `realdocs.py` / `filedlg.py`）没删，留着当备份，但主程序不再引用。

**这是整个项目最划算的一次减法：删掉一半代码，真实度反而上去了。**

### 2.3 棋子用现成美术 vs 用用户自己的图标

用桌面图标当棋子，一次解决三个问题：

1. **零美术成本**，而且每个用户的棋盘天生独一无二
2. 图标是 256px 系统原图（`SHIL_JUMBO` → `GetDIBits`），不是拉伸的小图，管理员权限也不用
3. "这个棋子是我的 PPT" 这件事本身就是笑点

代价是**棋子可能长得一样**——桌面上经常有七八个白纸文档图标。所以加了挑选策略：
8×8 特征向量去重 → 按色相分 6 个桶 → 每桶最多取 2 个、无彩色桶最多 1 个。
保证十种棋子颜色一定拉得开，玩家不会看错。

> 这里体现一个通用思路：**把"内容不可控"当成输入约束，用算法兜底，而不是要求用户整理桌面。**

### 2.4 发种子 vs 直接发棋盘

联机 A 模式（同盘竞速）最初打算只同步一个 `seed`，让两边各自用同一个随机序列生成棋盘。
实装时改成**直接发 140 个整数**。

理由：种子方案依赖两边 `random` 实现、调用顺序、Python 版本完全一致，一旦有一处不同，两边看到的是两块不同的板，
而且这种 bug 极难复现。140 字节对 TCP 和蓝牙都是零压力，**用 140 字节换掉一整类不确定性，非常值**。

### 2.5 抢锁仲裁 vs 房主串行

共享棋盘（B 模式）最初设计得很"正经"：`claim` 占位 → 房主发 350ms 租约 → `grant` → 才允许 `swap`，还考虑了乐观预测和回滚。

实装时砍成**先到先得**：客户端直接发 `swap`，房主是唯一权威，天然串行。
省掉了锁表、租约超时、"抢输了"的回滚抖动。手感反而更干脆——**延迟只影响你抢不抢得到，不会让画面抽一下**。

### 2.6 各看各的图标 vs 全员看同一张图

原方案：协议只传类型 id，每个人映射到自己的图标。
实际需求变了——大家想看到同一个画面。于是改成**房主把图标拼成一张 960×96 的 PNG，base64 传过去（约 30KB）**，一次传完。

一条经验：**需求变了就改方案，别为了"架构优雅"硬扛。**

### 2.7 传事件流 vs 传整盘快照

原设计是服务器广播 `clear / fall / spawn` 事件，客户端喂给现有动画层回放。
实装改成**传结算后的整块盘 + 这次消掉的位置 + 谁得的分**。

因为事件流要重放随机补充，客户端和房主的 `random` 一旦分叉，盘就歪了；而整盘只有 140 字节。
客户端只负责"闪一下再落定"，简单且不会分叉。

### 2.8 tkinter vs 手写 Win32 窗口

设置窗口要能输入中文昵称、能粘贴、能拖动、能最小化。候选是 tkinter 和手写 Win32。

tkinter 直接出局：打包用的解释器没带 Tk；就算带，两套 GUI 框架在一个进程里抢焦点、抢消息泵，和 SDL 的无边框窗口很容易打架。

于是：`RegisterClassW` + `CreateWindowExW` 开原生窗口，画面用 pygame 离屏渲染后 `StretchDIBits` 贴上去（字体配色和游戏内一致），
文字输入交给系统 `EDIT` 控件——**中文输入法、选区、粘贴全都免费**。
消息由主循环每帧 `PeekMessage/DispatchMessage` 驱动，单线程，不另开窗口线程。

> 通用思路：**能借系统组件就别自己实现**。输入法这种"看起来简单、做起来无底洞"的东西，尤其不要自己写。

## 三、分层：让"纯逻辑"待在中间

```
main.py                 入口 / 自检 / 命令行参数
  └── src/app.py        渲染与主循环：布局、缓动、连锁、计分、结算、联机接入
        ├── src/engine.py      纯逻辑：三消判定、重力、死局、洗牌、同步结算
        ├── src/winicons.py    平台适配：桌面枚举、256px 图标、壁纸、间距、DPI
        ├── src/netcore.py     传输：帧协议、TCP、UDP 广播、蓝牙 RFCOMM
        ├── src/netplay.py     联机状态机：房间、两种玩法、实时比分
        └── src/settings_win.py 窗口外壳：Win32 原生子窗口
```

依赖方向是单向的：**`engine.py` 不知道 pygame 存在，也不知道网络存在。**

这个切法带来三个白拿的好处：

1. **可测**——不用开窗口就能跑 60 步一致性和死局检测（`tools/smoke.py`）
2. **可当权威**——联机时房主直接用同一个 `resolve_swap()` 算分，单机和联机共用一套计分，不会出现"单机 1000 分、联机 800 分"
3. **可移植**——微信小程序版能复用同一套公式和随机数（`mulberry32` 对齐），就是因为逻辑层是干净的

> 判断分层对不对，有个简单标准：**中间层能不能被另一个完全不同的前端直接用。** 能，就说明切对了。

## 四、怎么验证："看不见的东西"最难测

这个项目的界面是"假装成桌面"，很多问题是肉眼看不出来的（比如 125% 缩放下格子错位、壁纸接缝对不上）。
所以验证手段本身就是设计的一部分：

| 手段 | 解决什么 |
|---|---|
| `python main.py --selftest` | 无窗口自检：布局、图标、计分、联机全链路，结果写日志 |
| `tools/smoke.py` | 60 步连续游走，比对显示层和数据层是否始终一致 |
| `tools/net_smoke.py` | 两个 `Game` 走真实 TCP，A/B 模式各跑一遍 |
| `tools/probe_exe_*.py` | 用**真实鼠标消息**点打包后的 exe，验证点击命中、洗牌、联机 |
| `tools/shot_*.py` | 离屏渲染出图，代替"我自己开一下看看" |
| `tools/shot_readme.py` | 出 README 那张图：临时假桌面 + 合成壁纸，**不碰真实文件名** |

截图工具那条尤其值得说：README 要放效果图，但直接截屏会把用户真实文件名和壁纸一起公开。
做法是把 `USERPROFILE` 指到一个临时目录（里面放"项目计划.docx"这类占位文件），壁纸用合成渐变，再离屏渲染。
**同一套渲染代码，换一个输入源，隐私就不出仓库。**

## 五、踩过的坑，和它们教的东西

| 坑 | 教训 |
|---|---|
| PyInstaller 打进上一版代码，用户打开还是旧界面 | `build/` 缓存不会因为改源码失效，**每次必须 `--clean` + 删 `build/`**；用自检日志里的参数核对版本 |
| `StretchDIBits` 第 12 参传成 `SRCCOPY`，窗口全白 | 那是 `iUsage`，要传 `DIB_RGB_COLORS = 0`；`SetBkColor` 在 gdi32 不在 user32 |
| 设置窗口关掉后键盘失灵 | 窗口打开期间 SDL 事件队列会堆积，**只认 QUIT，其余丢弃** |
| 用户根本找不到设置入口 | 功能做对了不等于能找到；**首次运行自动弹窗 + 底栏常驻按钮 + `Ctrl+J`** 三条路 |
| 记录页把历史最高分覆盖了 | 写存档要用"只升不降"的累加式更新，别整份覆盖 |

一条共同的教训：**这类"窗口 + 图标 + 打包"的项目，难的不是算法，是和操作系统打交道的那一层。**
所以每个平台调用都单独塞进 `winicons.py` / `settings_win.py`，出了问题能一眼定位到是哪一层的锅。

## 六、迭代节奏

九轮，每轮都能独立交付、独立验证：

```
第 1 轮  能跑起来：桌面图标 → 棋子，三消逻辑闭环
第 2 轮  像桌面：壁纸裁切、真实间距、256px 图标、选中框、文件名字体
第 3 轮  手感：缓动、碎屑、连锁倍率、死局检测与重排
第 4 轮  收尾：结算卡片、历史前十、`ESC` 记分退出
第 5 轮  减法：整屏 → 左半屏，砍掉复刻任务栏和假文档窗口
第 6 轮  打包：PyInstaller 单文件，自检塞进 exe
第 7 轮  联机评估：三种形态、三种权威模型，先写方案再动手
第 8 轮  联机实装：TCP + UDP 广播 + 蓝牙，A/B 两模式
第 9 轮  交互重构：玩法/联机搬进独立原生子窗口 + 首次弹窗引导
```

顺序上的两个刻意选择：

- **先做视觉真实度，再做联机。** 联机是"锦上添花"，而"看起来像不像桌面"决定了这个东西能不能用
- **第 5 轮专门做减法。** 不是等到收尾才删代码，而是发现"复刻不如借用"就立刻砍

## 七、如果重来，会改哪里

诚实版的复盘：

1. **一开始就该只占半屏。** 整屏覆盖 + 复刻任务栏浪费了大概两轮，最后全被删掉
2. **窗口层应该更早抽象。** 设置窗口是第九轮才做的，如果第一轮就把"渲染到离屏 Surface 再贴到 Win32 窗口"这条路走通，后面很多 UI 都能更早搬出棋盘
3. **联机应该先做"同种子竞速"再评估共享棋盘。** 直接上 B 模式，把最难的仲裁和同步一起做了，风险偏高（好在最后砍成先到先得，反而简单）
4. **还得补的**：蓝牙双机实测、多显示器、按 `onedir` 打包解决首启 2~3 秒延迟和杀软误报

---

## 八、一句话总结

> 先用约束把问题缩小，再用取舍把方案减到最薄，然后把纯逻辑锁在中间层，
> 最后用自动化手段去测那些"肉眼看不见"的地方。
